# Shared foundation: Spring Boot

Generated by the platform from the stack profile `spring-boot` 1.1.0. Do not edit by hand: change the configuration and generate again.

## What it gives a service

- RFC 7807 problem responses for every error, with no internal detail in a 500.
- Structured JSON logs on the console, with personal data redacted (`log-masking`: email) and the trace id on each line.
- An audit logger (`foundation.audit.AuditLogger`) that writes one line per event to the logger `audit`.
- Security: stateless, no CSRF for the API, health probes open (`auth`: jwt).
- OpenTelemetry tracing (`trace-sampling`: 0.1) and Actuator health probes.

- Kafka behind `foundation.messaging.EventSink`. A failed message is retried 3 times with exponential backoff (`foundation.messaging.retry-attempts`).
- A message that still fails after its retries is published to `<topic>.DLT`.
- A transactional outbox: `Outbox.publish(topic, key, payload)` inside your database transaction, relayed to Kafka at least once. Settings:
  `foundation.outbox.poll-interval-ms`, `batch-size`, `retention-days`.
- An inbox: `Inbox.firstTime(consumer, messageId)` inside the handler's transaction tells a consumer whether it has handled a message already.

## Using it in a service

In `services/<name>/settings.gradle`:

```groovy
includeBuild('../../foundation/spring-boot')
```

In `services/<name>/build.gradle`: `implementation 'foundation:foundation-spring-boot'`.

On the application class: `@EnableFoundation`.

## Database

The outbox tables are created by Flyway migrations in `db/foundation` (versions `V0_x`, which run before your own `V1`). Add the Flyway module
and the JDBC driver of your database to the service. Enable the outbox before the service's first migration runs: on a database that already
has `V1` applied, the lower versions are refused unless you set `spring.flyway.out-of-order=true`. The outbox SQL is standard SQL; the inbox
uses `ON CONFLICT DO NOTHING` (PostgreSQL).
