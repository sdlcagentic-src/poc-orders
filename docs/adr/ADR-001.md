title: PostgreSQL for Order Management orders
kind: data-store
context: "BC-001 owns orders with line items and a lifecycle (placed, confirmed, rejected,\
  \ cancelled). Order and line item data is relational and the status changes must\
  \ be transactional. REQ-010 requires that no confirmed order is lost on restart.\
  \ CreateOrderRequest carries customerEmail, which REQ-012 says must be stored only\
  \ where needed. The order must also keep the email so that confirmation, rejection\
  \ and cancellation events can carry it."
decision: "Order Management stores orders and line items in its own PostgreSQL database,\
  \ accessed through Spring Data JPA with Flyway migrations. Status changes are committed\
  \ in a single transaction, and the customer email is held only in the order record."
alternatives:
- option: MongoDB document store
  rejected_because: "Orders are small, well-structured aggregates with simple relations.\
    \ A document store adds a less familiar technology and gives weaker multi-record\
    \ transactional guarantees than the team needs for lifecycle changes."
- option: In-memory store with periodic snapshots
  rejected_because: Violates REQ-010 because confirmed orders could be lost when the
    service restarts.
- option: Shared database with Inventory Management
  rejected_because: Couples two services at the schema level and violates the separate-services
    constraint REQ-013.
consequences: "Durable, ACID storage makes REQ-010 straightforward and the technology\
  \ is boring and well supported by Spring Boot. Order Management needs its own database\
  \ instance and migration pipeline. The email column needs access control and must\
  \ be excluded from logging."
