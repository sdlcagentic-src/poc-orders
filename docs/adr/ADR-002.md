title: PostgreSQL with row-level locking for Inventory stock
kind: data-store
context: "BC-002 owns stock levels and reservations. Reserving stock must be atomic\
  \ across all items of an order, and REQ-011 requires stock never to go negative\
  \ even when two customers order the last item at once. Stock levels are also listed\
  \ for staff. The data is simple, relational and write-contended."
decision: "Inventory Management stores stock levels and reservations in its own PostgreSQL\
  \ database. Reservations run in one transaction that locks the affected stock rows,\
  \ using SELECT FOR UPDATE in a consistent product order, plus a CHECK constraint\
  \ that quantity is greater than or equal to zero."
alternatives:
- option: Redis with atomic decrement scripts
  rejected_because: Gives fast atomic counters but weaker durability and no multi-item
    transactional guarantee without custom scripting. It is also less suitable for
    the reservation history.
- option: Optimistic locking with version column and retries
  rejected_because: Under contention on popular products it causes retry storms. Pessimistic
    locking is simpler and sufficient for the expected load.
- option: MongoDB with multi-document transactions
  rejected_because: Adds an unfamiliar technology for a relational and transactional
    problem.
consequences: "The database enforces the non-negative invariant even if application\
  \ code has a bug, which satisfies REQ-011. Consistent lock ordering is needed to\
  \ avoid deadlocks. Hot products serialize on their row, which is acceptable at this\
  \ scale."
