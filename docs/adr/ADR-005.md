title: Service-per-context deployment with React SPA
kind: cross-cutting
context: "The system must be delivered as separate services with a small web UI of\
  \ two or three screens (REQ-013). The contexts each expose their own contracts,\
  \ and the UI needs to place, view and cancel orders and view stock levels. Payment,\
  \ shipping and returns are out of scope (REQ-014), so no services for them are needed."
decision: "Build exactly three Spring Boot 3 services on Java 21, one per context,\
  \ each deployed independently with its own database, plus a single React SPA served\
  \ behind an API gateway that routes to the Order and Inventory REST APIs. No services\
  \ or modules are created for payment, shipping or returns."
alternatives:
- option: Modular monolith
  rejected_because: Contradicts the constraint that the system is delivered as separate
    services.
- option: Micro-frontends per context
  rejected_because: Excessive for a two or three screen UI and applies abstraction
    before the Rule of Three justifies it.
- option: Add placeholder services for payment and shipping
  rejected_because: Out of scope per REQ-014 and would add untested complexity.
consequences: "Teams can deploy and scale services independently and the UI stays\
  \ simple. There is operational overhead from three services and a gateway. Scope\
  \ boundaries are explicit, so payment, shipping and returns requests must be rejected\
  \ or planned separately."
