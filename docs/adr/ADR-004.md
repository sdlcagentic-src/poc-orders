title: Kafka event backbone with transactional outbox
kind: cross-cutting
context: "The contexts communicate asynchronously through orders.* and inventory.stock.*\
  \ channels, and Notifications is a conformist to Order Management. REQ-010 says\
  \ no confirmed order is lost if any component restarts, so events must not be lost\
  \ between a database commit and publication. REQ-013 requires separate services."
decision: "Use Apache Kafka as the broker via Spring Kafka. Each publisher writes\
  \ events to an outbox table in the same transaction as its state change and a relay\
  \ publishes them with at-least-once delivery, while consumers are idempotent."
alternatives:
- option: Direct publish after commit (dual write)
  rejected_because: "A crash between commit and publish loses the event, which breaks\
    \ REQ-010."
- option: RabbitMQ
  rejected_because: "Capable, but Kafka gives durable replayable logs that help recovery\
    \ after consumer restarts, and the AsyncAPI channel model maps cleanly to topics."
- option: Synchronous REST calls between services for all flows
  rejected_because: Couples availability of services and makes Notifications failures
    affect order handling.
consequences: Events survive restarts and consumers can replay. Developers must write
  idempotent handlers and maintain outbox tables and relays. Duplicates are possible
  and must be tolerated.
