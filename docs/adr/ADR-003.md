title: PostgreSQL for Notification dispatch records
kind: data-store
context: "BC-003 sends emails when orders are confirmed, rejected or cancelled and\
  \ publishes events that record dispatch without the email address (EmailSentPayload).\
  \ It needs to avoid duplicate or lost sends when events are redelivered, so it needs\
  \ a small durable record of processed orders and dispatch state. REQ-012 says the\
  \ email address must be stored only where needed and never logged. REQ-010 requires\
  \ that no confirmed order is lost across restarts, which includes the confirmation\
  \ notification."
decision: "Order Notifications keeps a small PostgreSQL database holding an idempotency\
  \ and dispatch record per order event, keyed by orderId and event type. It stores\
  \ no email address after the send succeeds and never persists it beyond what a pending\
  \ retry needs."
alternatives:
- option: Stateless service with no store
  rejected_because: "Cannot deduplicate redelivered events or retry failed sends after\
    \ a restart, so emails could be lost or duplicated."
- option: Redis for idempotency keys
  rejected_because: "Adds another technology and offers weaker durability, while the\
    \ team already operates PostgreSQL for the other services."
- option: Store full email history with addresses
  rejected_because: Violates the data minimisation goal of REQ-012 because the address
    would be kept without need.
consequences: "Idempotent consumption and safe retries are possible. A third database\
  \ instance is needed, though it is small. Any pending-retry email data must be purged\
  \ after delivery."
