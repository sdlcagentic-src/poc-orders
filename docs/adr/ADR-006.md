title: Performance of order placement through bounded synchronous work
kind: cross-cutting
context: "Placing an order must respond within 2 seconds at the 95th percentile under\
  \ normal load (REQ-009). Order placement persists the order and announces orders.placed.\
  \ Stock verification is delivered by the inventory.stock.checked event, and confirmation,\
  \ rejection and notification happen asynchronously."
decision: "The createOrder call only validates, persists the order in status placed\
  \ and writes the outbox event, then returns 201. Stock checking, confirmation and\
  \ email sending run asynchronously. HTTP clients use connection pooling and timeouts,\
  \ and a load test against the 2 second p95 target runs in the build pipeline."
alternatives:
- option: Synchronous stock reservation inside the createOrder request
  rejected_because: "Ties the response time to Inventory availability and latency,\
    \ putting the 2 second target at risk and creating temporal coupling."
- option: Caching stock levels in Order Management
  rejected_because: "Introduces stale data and duplicate ownership of stock, risking\
    \ violation of stock consistency."
consequences: "Response time depends only on one local transaction, so the target\
  \ is easily met. Clients see the status placed first and must poll or view the order\
  \ to see the outcome, which the UI must handle."
